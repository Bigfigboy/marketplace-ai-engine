# AI Engine — передача Backend 2 (handoff)

Кратко: AI Engine — отдельный сервис FastAPI, который исполняет AI-агентов по единому HTTP API.
Backend 2 (Supabase) отвечает за пользователей, роли, каталог, заявки, подписки и RLS и вызывает движок
сервер-к-серверу. Связанные документы:

- [API_CONTRACT.md](API_CONTRACT.md) — endpoints, JSON, авторизация, ошибки (контракт);
- [SUPABASE_INTEGRATION.md](SUPABASE_INTEGRATION.md) — идентичность, роли, `agent_runs`, файлы, БД;
- [INTEGRATION_CHECKLIST.md](INTEGRATION_CHECKLIST.md) — совместное тестирование;
- [API_DOCUMENTATION.md](API_DOCUMENTATION.md), [ARCHITECTURE.md](ARCHITECTURE.md),
  [FREE_LLM_PROVIDERS.md](FREE_LLM_PROVIDERS.md), [CLOUD_DEPLOY.md](CLOUD_DEPLOY.md) — подробности.

## 1. Границы ответственности

| Область | AI Engine (мы) | Backend 2 |
|---|---|---|
| Пользователи, Auth, роли `business/developer/admin` | принимает доверенную идентичность из engine token | Supabase Auth, `profiles` |
| Каталог, карточки, заявки, публикация | `GET /agents` — метаданные своих агентов | `agents`, `agent_submissions`, API каталога |
| Подключение бизнеса к агенту | не проверяет | `connect_requests`, проверка до вызова движка |
| Исполнение агентов | `marketing`, `support`, `hr` (демо) | вызывает движок; сторонних агентов движок не исполняет |
| Файлы | своя копия для обработки (PDF/DOCX/TXT, RAG) | Supabase Storage — хранилище для пользователей |
| Журнал запусков | технический `agent_runs` движка | бизнес-`agent_runs` в Supabase со ссылкой на `run_id` |
| Изоляция данных | по `company_id` из токена (файлы, база знаний, запуски, лимиты) | RLS в Supabase |
| LLM-провайдеры, лимиты, стоимость | да | — |

## 2. Архитектура AI Engine

```
Backend 2 ──HTTPS, Bearer <engine token>──► AI Engine (FastAPI)
                                              │
            CORS → лимит размера тела → request id/заголовки → аутентификация + rate limit
                                              │
            POST /agents/{slug}/run ─► runner: опции → язык → файлы (ACL по company_id)
                                       → атомарная проверка лимитов (запись "running")
                                       → guardrails (prompt injection, HR-политика)
                                       → агент (marketing | support | hr) → LLM-провайдер
                                       → стоимость → agent_runs → единый ответ
                                              │
      LLM: mock | groq | gemini | openrouter (:free) | ollama (локально) | openai (платно, только явно)
      Файлы: проверка формата → извлечение текста в изолированном процессе (лимиты времени/памяти)
             → приватное хранилище STORAGE_DIR/<company_id>/ → фрагменты для RAG (BM25)
      БД: SQLite (демо) или PostgreSQL; миграции Alembic
```

Ключевые свойства для интеграции:

- **Один endpoint для всех агентов**: `POST /agents/{slug}/run` с единым форматом запроса и ответа.
- **Идентичность только из токена**; тенант = claim `company_id`; данные разных компаний не пересекаются
  (чужие объекты → 404).
- **Журнал без текстов**: движок хранит метаданные запусков, но не запросы и ответы.
- **Новый агент** подключается модулем в `app/agents/` + `AGENT_MODULES`, без изменения API; загрузка
  непроверенного стороннего кода не поддерживается.

## 3. Проверка совместимости (результаты)

| Вопрос | Ответ |
|---|---|
| Можно ли вызывать API из другого бэкенда? | Да. Обычный HTTP/JSON, Bearer-токен, без cookies и CSRF. Сервер-к-серверу CORS не нужен. Проверено тестами `tests/test_backend2_contract.py` (17) |
| Какая авторизация реализована? | (1) JWT, подписанный общим секретом `JWT_SECRET` (`HS256/384/512`), с проверкой `exp`, `sub`, `company_id`, опционально `aud`/`iss`, с автосозданием компании и пользователя по внешним id; (2) API-ключи `aie_...` (SHA-256 в БД), выпуск только через CLI |
| Подходит ли токен Supabase Auth напрямую? | **Нет**: в нём нет `company_id`, `role` = `authenticated`, другая аудитория и возможна асимметричная подпись. Нужен engine token от Backend 2 (SUPABASE_INTEGRATION.md §3) |
| Как изолированы компании? | Каждый запрос к файлам, фрагментам базы знаний, запускам и статистике фильтруется по `company_id` из токена; доступ к чужому объекту → 404; поиск support идёт только по базе знаний своей компании |
| Как передаются файлы? | Байтами через `POST /files/upload` (multipart) → `file_id` движка → `file_ids` при запуске. Ссылки на Supabase Storage движок не принимает |
| Какие endpoints требуют прав администратора? | Платформенного администратора нет. Роль `admin` в токене = администратор **своей компании**: загрузка базы знаний (`purpose=knowledge_base`), просмотр всех файлов/запусков/статистики компании, удаление любых файлов компании. Управление ключами — только CLI на сервере |
| Что передавать в Supabase? | `run_id` и метаданные из ответа (статус, токены, стоимость, время, провайдер, код ошибки), `file_id` движка, соответствие карточек каталога и engine slug (SUPABASE_INTEGRATION.md §8) |
| Можно ли хранить БД движка в Supabase? | Только в **отдельной схеме** (`ai_engine`) или в отдельной БД; в `public` конфликтует имя `agent_runs`. Отдельная схема проверена на PostgreSQL 16 |

### Проблемы, которые возникнут при интеграции, и решения

| # | Проблема | Решение |
|---|---|---|
| 1 | Токен Supabase не принимается движком | Backend 2 выпускает engine token (5 мин) общим секретом |
| 2 | В Supabase нет понятия `company_id` для движка | Согласовать, какой id считается тенантом (владелец-бизнес или организация) |
| 3 | Роли не совпадают (`business/developer/admin` и `admin/member`) | Таблица сопоставления в SUPABASE_INTEGRATION.md §2 |
| 4 | Две таблицы `agent_runs` | Одна строка Backend 2 на вызов, `engine_run_id UNIQUE`; БД движка — не в `public` |
| 5 | Казахский язык: движок принимает `kk`, а не `kz` | Backend 2 передаёт `kk` (иначе `422 validation_error`) |
| 6 | Render работает в mock-режиме: ответы помечены «не ИИ», стоимость 0 | Для показа с реальной моделью — §4 |
| 7 | Ollama запущен локально на Windows и недоступен облачному серверу | Не открывать Ollama в интернет; варианты — §4 |
| 8 | Render Free: «засыпание» ~1 мин, долгие запуски до 120 с | Таймаут HTTP-клиента Backend 2 ≥ 150–180 с; показывать индикатор ожидания |
| 9 | Render Free: диск эфемерный — файлы, база знаний и журнал движка пропадают при перезапуске | На `404 file_not_found` — повторная загрузка; для постоянного стенда — PostgreSQL + постоянный диск |
| 10 | Нет ключа идемпотентности у `POST /agents/{slug}/run` | Не повторять автоматически, кроме 429/503/504 по `Retry-After` |
| 11 | Демо-лимит 10 запусков в сутки на пользователя (`DEMO_MODE=true`) | На время совместных тестов увеличить `DAILY_RUN_LIMIT_PER_USER` на стенде |
| 12 | Rate limit движка хранится в памяти процесса | Достаточно для одной реплики; при масштабировании — Redis (не реализовано) |
| 13 | Сторонние агенты не исполняются движком | Каталог Backend 2 различает engine-агентов (`engine_slug`) и прочих |
| 14 | Движок не знает о подписках | Проверка `connect_requests` — в Backend 2 до вызова |
| 15 | Сообщения ошибок на английском | Ветвиться по `error.code`, тексты для пользователя — в Backend 2/фронтенде |

## 4. Окружения и LLM

| Окружение | LLM | Когда использовать |
|---|---|---|
| Render Free (сейчас) | `LLM_PROVIDER=mock` — без ключей, ответы помечены `mode: "mock"` | интеграционные тесты API, контракта, авторизации, файлов, ошибок |
| Render Free + бесплатный провайдер | `groq` / `gemini` / `openrouter` (ключ в Render Environment, владелец ключа 18+) | демо с реальной моделью в облаке, без затрат |
| Локально на Windows | `ollama` + `qwen3` (сейчас у команды) | разработка/демо на одном компьютере |

Ollama на Windows недоступен облачному серверу. Варианты:

1. **Рекомендуется для облака:** бесплатный провайдер на Render (Groq/Gemini/OpenRouter), см. FREE_LLM_PROVIDERS.md.
2. **Для локального совместного теста:** запустить весь движок на том же Windows-компьютере, где Ollama
   (`LLM_PROVIDER=ollama`), а Backend 2 направить на него (`ENGINE_URL=http://<IP компьютера в локальной
   сети>:8000`, uvicorn с `--host 0.0.0.0`, разрешить порт в брандмауэре Windows только для локальной сети).
3. **Не рекомендуется:** публиковать Ollama в интернет туннелем — у Ollama нет авторизации; если туннель
   всё же нужен, публикуйте **движок** (он требует токен), а не Ollama, и только на время теста.

## 5. Инструкция для Backend 2

1. **Получить от нас:** `ENGINE_URL` (адрес стенда) и `ENGINE_JWT_SECRET` (по защищённому каналу, не в чате
   и не в git). Мы задаём в движке: `JWT_SECRET=<тот же секрет>`, `JWT_AUDIENCE=ai-engine`,
   `JWT_ISSUER=marketplace-backend`.
2. **Хранить у себя в env:** `ENGINE_URL`, `ENGINE_JWT_SECRET`. Никогда не отдавать секрет во фронтенд.
3. **Реализовать выпуск engine token** (SUPABASE_INTEGRATION.md §3): `sub` = id пользователя Supabase,
   `company_id` = согласованный id бизнеса, `role` = `admin` для владельца бизнеса, иначе `member`,
   `exp` = 5 минут.
4. **Перед вызовом** проверить в Supabase: агент опубликован, связан с engine slug, бизнес подключён
   (`connect_requests`).
5. **Вызывать** `POST {ENGINE_URL}/agents/{slug}/run` (таймаут ≥ 150 с), передавать `language`
   `ru`/`kk`/`en` или не передавать.
6. **Файлы:** скачать из Storage → `POST /files/upload` с нужным `purpose` → сохранить `file_id` движка →
   передать в `file_ids`; при удалении — `DELETE /files/{id}`.
7. **Записать** результат в свою `agent_runs` с `engine_run_id` (уникально), в т.ч. для ошибок
   (`error.details.run_id`).
8. **Обрабатывать ошибки** по `error.code` (API_CONTRACT.md §3); 401 → перевыпустить токен; 429 → `Retry-After`.
9. **Мониторинг:** `GET {ENGINE_URL}/health` (публичный).
10. Пройти [INTEGRATION_CHECKLIST.md](INTEGRATION_CHECKLIST.md) вместе с нами.

## 6. Что нужно согласовать

1. Какой id — тенант (`company_id`): id профиля владельца бизнеса или отдельной организации.
2. Сопоставление ролей (SUPABASE_INTEGRATION.md §2), в т.ч. нужен ли доступ `developer` к демо-агентам.
3. Значения `JWT_AUDIENCE`/`JWT_ISSUER`, срок жизни токена, канал передачи секрета и порядок его ротации.
4. Схема вызова: только через Backend 2 (рекомендуется) или напрямую из браузера (тогда `CORS_ORIGINS`).
5. Структура записи в `agent_runs` Supabase и уникальный `engine_run_id`; хранить ли тексты (для HR — нет).
6. Колонка соответствия «карточка каталога ↔ engine slug» и как помечаются сторонние агенты.
7. Хранение `file_id` движка рядом с объектами Storage; удаление файлов в обеих системах.
8. Где живёт БД движка (отдельная БД или схема `ai_engine`, не `public`).
9. Лимиты на время совместных тестов (`DAILY_RUN_LIMIT_PER_USER`, `RATE_LIMIT_PER_MINUTE`) и в продакшене.
10. Какой LLM-провайдер на общем стенде (mock / бесплатный облачный) и кто владелец ключа.

## 7. Известные ограничения демо-агентов

- **Все три агента — демонстрационные.** Качество ответов зависит от модели; в облаке сейчас mock (не ИИ).
  Реальные бесплатные провайдеры в среде разработки не вызывались — проверены на имитации их API.
- **Marketing:** создаёт только черновики, ничего не публикует; не знает актуальной статистики рынка;
  цифры помечаются для проверки.
- **Support:** поиск по базе знаний лексический (BM25, без эмбеддингов): перефразированные вопросы
  находятся хуже; отвечает только по загруженным документам, иначе `escalation_required`; обращения
  менеджеру только готовятся (`delivered: false`), интеграции с CRM нет.
- **HR:** одно резюме за запрос, без ранжирования и решений о найме; персональные данные маскируются перед
  отправкой в LLM; маленькие локальные модели (qwen3:1.7b) часто дают неполный JSON — сводка дополняется
  фактами из документа, при пустом ответе — ошибка `llm_invalid_output`.
- **Файлы:** нет OCR (сканы → `ocr_required`); PDF/DOCX до 10 MB.
- **Казахский язык:** качество зависит от модели; рекомендуется проверка носителем.
- **Масштабирование:** синхронные запросы, rate limit в памяти процесса, на Render Free — эфемерный диск.
